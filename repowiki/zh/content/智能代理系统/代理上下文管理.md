## 引言
本文档全面阐述代理上下文（Agent Context）的构建与管理机制。系统通过`builder.py`根据运行时环境动态组装执行上下文，整合市场状态、事件数据与历史记忆。`output_store.py`实现分析结果的持久化存储至Redis，支持异步写入与幂等性保障。`validators.py`确保代理输出符合`contracts.py`定义的统一数据契约。`registry.py`在上下文构建过程中提供元信息注册服务，`utils.py`提供路径操作等辅助函数。

## 代理上下文构建机制

代理上下文构建的核心是`build_agent_context`函数，它根据代理类型从完整上下文中提取所需字段。该过程遵循严格的访问控制策略，确保每个代理只能访问其授权范围内的数据。

```mermaid
sequenceDiagram
participant Builder as "builder.py"
participant Profiles as "profiles.py"
participant Utils as "utils.py"
participant Validators as "validators.py"
participant Registry as "registry.py"
Builder->>Validators : validate_agent(agent)
alt 代理类型有效
Builder->>Builder : agent = agent.lower()
Builder->>Builder : 检查是否为fusion代理
alt 是fusion代理
Builder->>Builder : 深拷贝完整上下文
Builder->>Builder : _drop_internal_fields(ctx)
Builder->>Registry : 添加_context_meta
Builder-->>Builder : 返回完整上下文
else 不是fusion代理
Builder->>Profiles : get_allowed_paths(agent)
alt 路径存在
Builder->>Builder : 初始化输出上下文
loop 遍历允许路径
Builder->>Utils : get_by_path(full_context, path)
Builder->>Utils : set_by_path(out, path, val)
end
Builder->>Builder : _drop_internal_fields(out)
Builder-->>Builder : 返回裁剪后上下文
else 路径不存在
Builder->>Validators : forbid_full_context(agent)
end
end
else 代理类型无效
Validators-->>Builder : 抛出ValueError
end
```

- **流式存储**：使用Redis Stream按时间序列存储历史记录

- **幂等性保障**：通过时间戳和唯一键确保数据一致性

## 注册表与配置管理

`registry.py`是代理上下文系统的核心配置中心，定义了所有代理的元信息和访问策略。

```python
AGENT_REGISTRY: dict[str, AgentContextContract] = {
    "force_stats": {
        "agent": "force_stats",
        "role": "liquidation_structure",
        "scope": ["micro", "short"],
        "uses_crowd_state": True,
        "allows_cross_timeframe_inference": False,
        "forbidden_semantics": [
            "trend_forecast",
            "strategy_advice",

        "allowed_paths": [
            "market_state.micro_term.state",
            "market_state.short_term.direction",

            "market_state.long_term.veto",

            "crowd_state.crowding_level",

            "crowd_state.consistency",
            "crowd_state.funding_pressure",
```

每个代理配置包含：
- **角色（role）**：定义代理的分析职责
- **作用域（scope）**：定义时间尺度边界
- **允许路径（allowed_paths）**：字段白名单
- **群体状态使用（uses_crowd_state）**：是否可访问群体心理数据

## 上下文构建流程示例

以下是一个完整的上下文构建流程示例：

```mermaid
flowchart TD
A[开始] --> B["创建完整上下文 full_context"]
B --> C["调用 build_agent_context('force_stats', full_context)"]
C --> D["validate_agent('force_stats')"]
D --> E["agent = 'force_stats'"]
E --> F["agent != 'fusion'"]
F --> G["get_allowed_paths('force_stats')"]
G --> H["返回 force_stats 的 allowed_paths"]
H --> I["初始化输出上下文 out"]
I --> J["遍历 allowed_paths"]
J --> K["get_by_path(full_context, path)"]
K --> L["set_by_path(out, path, val)"]
L --> M{"所有路径处理完毕?"}
M --> |否| J
M --> |是| N["_drop_internal_fields(out)"]
N --> O["返回构建的上下文"]
O --> P[结束]
```

该流程确保了：
1. 代理身份验证
2. 访问权限控制
3. 敏感字段过滤
4. 数据完整性保障

## 常见问题与排查方法

### 常见上下文构建失败原因

| 问题类型 | 原因分析 | 排查方法 |
|---------|--------|--------|
| 未知代理 | 代理名称未在`AGENT_REGISTRY`中注册 | 检查`registry.py`中的注册表配置 |
| 权限不足 | 代理请求了不允许的字段路径 | 检查`allowed_paths`配置 |
| 完整上下文请求失败 | 非fusion代理请求完整上下文 | 确认代理类型是否为fusion |
| 字段缺失 | 路径格式错误或字段不存在 | 验证路径格式和数据源完整性 |
| 类型错误 | 数据类型不符合契约定义 | 检查`contracts.py`中的类型定义 |

### 排查步骤
1. **验证代理名称**：确保代理名称正确且已注册
2. **检查配置文件**：确认`registry.py`中的配置正确
3. **验证输入数据**：确保完整上下文包含所需字段
4. **调试路径解析**：使用`get_by_path`测试路径可达性
5. **查看日志信息**：检查异常堆栈和错误消息

## 结论
代理上下文管理系统通过模块化设计实现了安全、高效的上下文构建与管理。核心机制包括：
- 基于注册表的代理元信息管理
- 基于白名单的字段访问控制
- 敏感数据过滤与清理
- Redis持久化存储与幂等性保障
- 完整的校验与错误处理机制

该系统确保了不同代理在各自权限范围内安全地访问所需数据，同时通过统一的数据契约保证了系统的一致性和可维护性。
